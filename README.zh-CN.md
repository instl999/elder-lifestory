这是一套手工交付回忆录项目的工具，依据 LifeStory 产品规格说明 v2 构建。代码和文档里的章节编号（§）都指向这份规格说明；规格说明本身不在本仓库中。

---

## 这是什么，刻意不是什么

规格说明写得很明确：第一版**不是**面向消费者的应用。§14 要求先手工交付五到八个案例，量清楚操作员的时间到底花在哪里，再把最耗时的那一步自动化。§19 把面向家属的访谈界面放在第 2 阶段。

所以这是一套**操作员的工作台**，不是让家属直接使用的产品：

- 一个命令行工具，一个人一次跑一个案例
- 这个案例需要的第 0 阶段文档：同意书、访谈指南、质检清单
- 决定第 1 阶段该做什么的两件测量工具

现在就做面向家属的界面，等于为一个还不存在的用户做产品。

### 它能做什么

| | |
|---|---|
| **转写** | 录音 → 转写稿，用本机 Whisper 完成，可断点续传，并列出需要核对的人名和日期 |
| **导入** | 转写稿 → 带说话人和时间戳的语句 |
| **提取** | 语句 → 故事卡片、人物、地点、事实条目、原话引语，每条记录都注明出处 |
| **审阅** | 和讲述人一张张过卡片：放行给家属、保密，或者以后再定 |
| **校验** | 确定性的校验程序：时间顺序、人名、引语忠实度、同意、访问权限 |
| **核对** | 最多 25 条的家属核对单，15 分钟内能做完，答复一次录完 |
| **成稿** | 先出全书构想供家属确认，再只用已放行的材料写章节 |
| **导出** | Markdown 书稿、可编辑的 DOCX、印刷规格、可携带的档案 |
| **测量** | 分阶段工时和问题产出率，即第 0 阶段的两件测量工具 |

## 安装

需要 Python 3.11 或更高版本。在项目文件夹里运行：

```bash
pip install -e .
```

在项目文件夹里建一个名为 `.env` 的文件，写一行 `LIFESTORY_API_KEY=...`（用记事本就行；`.env` 已被 git 忽略）。然后运行：

```bash
python -m lifestory doctor --online
```

`doctor` 会检查 Python 版本、各项依赖、API 密钥、模型服务的连通性和转写模型，缺什么就告诉你怎么补。命令都用 `python -m lifestory <命令>` 的形式运行；只有当 Python 的 Scripts 文件夹在 PATH 里时，才能直接用 `lifestory` 这个简写。

提取和起草通过 [`llm.py`](lifestory/llm.py) 调用大语言模型，这是整个代码里唯一知道“供应商”存在的模块（§11）。默认使用 DeepSeek 的 OpenAI 兼容接口和 `deepseek-flash` 模型；在 `.env` 里设置 `LIFESTORY_API_BASE` 和 `LIFESTORY_MODEL` 可以改用别的服务。转写在**本机**用 Whisper 完成，不需要密钥。其余所有功能（校验、核对单、导出、测量）都离线运行。

**把转写稿发给外部模型服务，需要单独的同意记录。** 没有 `third_party_services` 这一项同意，提取会直接拒绝运行（§12.1）；讲述人的同意书里也应写明是哪家服务商。

案例数据存放在 `cases/` 目录，已被 git 忽略。那是真实的人生，不进版本库（§12.1）。

## 跑一个案例

完整流程见 [`operating-kit/zh/00-操作手册.md`](operating-kit/zh/00-操作手册.md)。**不用记步骤顺序：** `python -m lifestory status <案例>` 的最后一行永远告诉你下一步做什么，以及该用哪条命令。

```bash
# 1. 建立案例：家属使用的语言，以及档案由谁继承（§12.4）。
python -m lifestory new wang --owner "王秀英" --preferred "王奶奶" --language zh \
  --birth-year 1941 --sponsor "陈建国" --inheritor "陈建国"

# 2. 录音之前先取得同意（§12.1）。
python -m lifestory consent grant wang recording --by "王秀英" --role story_owner
python -m lifestory consent grant wang ai_processing --by "王秀英" --role story_owner
python -m lifestory consent grant wang third_party_services --by "王秀英" --role story_owner

# 3. 在本机转写，用已知的人名做提示。
#    然后对照录音，逐个核对它列出的人名和日期。
python -m lifestory transcribe wang recordings/session-1.m4a --hint "陈建国,东昌坊口"
python -m lifestory ingest wang cases/wang/transcripts/session-1.txt

# 4. 生成故事卡片。
python -m lifestory extract wang

# 5. 和讲述人一起过卡片：放行、保密，或以后再定（§12.2）。
python -m lifestory review wang

# 6. 家属核对单，然后录入家属的答复（§7.4）。
python -m lifestory confirm wang
python -m lifestory answers wang

# 7. 全书构想交家属确认，然后写章节（§9）。
python -m lifestory direct wang
python -m lifestory draft wang

# 8. 校验、导出、付印。
python -m lifestory check wang --export
python -m lifestory export wang
```

英文案例的流程完全一样，用 `--language en`（默认值）即可。

### 中文案例

建立案例时设 `--language zh`（简体）或 `--language zh-Hant`（繁体），家属能看到的所有内容都会跟着这个语言走：家属核对单、全书构想，以及书本身，包括扉页和版权页、“第一章”式的章节标号、段首空两格，DOCX 里的中文字体设为宋体/黑体（繁体用新细明体）。给操作员看的输出仍是英文。

- **转写**：中文默认用 Whisper `small` 模型（`base` 把这本书自己的书名“朝花夕拾”转成了“招花西石”）。所有文字统一转成案例使用的简体或繁体（Whisper 会随意混用两种字形），标点也会修正。用 `--hint` 给出的人名，会在每 30 秒音频里重新提示一次。
- **人名核对清单**：用 jieba 词性标注，加上中文人名的特征来找人名，包括姓氏、“阿”字小名，以及“长妈妈”“衍太太”这类亲属称谓式的叫法；同音的名字会归到一组，因为中文识别出错主要就是同音字（“王秀英”被听成“王秀瑛”）。
- **其他工具生成的转写稿**也能直接用：全角冒号（王秀英：……）、讯飞的“说话人1/说话人2”标签、“采访者/受访者”都能识别；而说话动词后面的冒号（他说：“……”）会正确地留在句子里，不会被当成说话人标签。
- **文书**在 [`operating-kit/zh/`](operating-kit/zh/) 里：讲述人的知情同意书、委托人与家属的同意书（都是为当面朗读而写的中文），以及中文版的操作手册、访谈指南（含协助模式）、质检清单和讲述人离世时的处理原则。访谈问题是为这一代人专门改写的，涉及称呼、谦辞、方言，以及如何对待那些艰难的年代。中英文档的对照见 [`operating-kit/README.md`](operating-kit/README.md)。

实测准确率，以及如何测量你自己的录音：见 [`samples/README.zh-CN.md`](samples/README.zh-CN.md)。

### 普通话演示：从录音到成书

[`samples/zh/run_demo.py`](samples/zh/run_demo.py) 把两段公有领域的普通话录音（《朝花夕拾》的朗读录音，共 25 分钟）从 `new` 一直跑到可印刷的 DOCX，全程调用真实的 DeepSeek 接口。其中两个需要人来做的步骤由脚本代为完成，并在运行时打印出来：一是操作员对照录音的核对（只按人名核对清单改，没有逐句跟听），二是讲述人和家属的决定。

| 阶段 | 结果 |
|---|---|
| 导入 | 2 次访谈，159 行，讲述人的话共 5,158 字 |
| 提取 | 16 张故事卡片、51 条事实条目、38 条原话引语，用时约 3.5 分钟 |
| 审阅 | 放行 12 张，保密 2 张，2 张留给讲述人决定（它们与一张保密卡片共用原话） |
| 核对 | 家属核对单 3 条，每条都点名鲁迅：“长妈妈是鲁迅的保姆，又叫阿长。” |
| 构想 | 6 章，围绕一条主线“谁肯把真话说给他听”，并列出下次访谈该补问的空白 |
| 起草与校验 | 2,633 字，约 19 页；每条引语都能溯源；标出一处重复段落 |

成品在 [`samples/zh/demo_book/`](samples/zh/demo_book/)。打开 DOCX 就能看到家属拿到手的样子：6×9 英寸开本、宋体、“第一章”标号、中文读者习惯的段首缩进。

仔细通读后发现的问题，以及它们对真实案例意味着什么：

- **书很薄。** 25 分钟的讲述只能成书约 19 页，其中大半是扉页和章首页。起草模型被要求不许注水，它确实没有注水，还在编辑备注里写明了（例如“素材偏薄（两张卡，强度 3–4），本章短于 1400 字”）。真实案例需要完整的几次访谈。
- **核对清单没标出的转写错误会进书。** “他胖胖的，和矮”（应为“和蔼”）和“推它呢”（应为“她”）都留了下来，因为脚本只改了清单里列出的错。真实的操作员要跟着录音逐句听。
- **编造的细节仍是最大的风险。** 有六句话录音里从来没有说过，例如“病家只得典衣当物”和“这两句话，我并排放着”。这六句全部出现在 `check` 现在打印的抽查清单里。详见[已知不足](#已知不足)。
- **起草模型的编辑备注值得一读。** 它会标出自己改过的字（“‘震怂’按通行写法作‘震悚’，请核对”），也会说明哪些引语因为转写有误而没有采用。

## 代码强制执行的四条约束

这四条不是配置项。它们是规格说明里承重的部分，之所以写死在代码里，正是因为赶工期的时候最容易被放松。

**讲述人没有放行的内容，一律到不了家属手里。** 语句默认是 `owner_only`（仅讲述人可见），只有逐条明确放行、并记录下是谁做的决定，才会向外公开。这条规则适用于*由它们衍生出的一切*，不只是故事卡片：一条事实条目能否公开，取决于它依据的每一条语句，而且每次读取时现算、不存储，所以不可能“过期”成更宽松的状态。标为 `restricted`（私密，即 §12.2 所说的私下倾诉）的材料会把这个标记传递到它的原始语句上，没有 `--force` 和一段书面说明就不能放行。

这由三道互相独立的锁把守：[`models.py`](lifestory/models.py) 里的 `Archive.visible_to`、`confirm.build` 的受众过滤，以及 [`validators.py`](lifestory/validators.py) 里的 `check_access` / `check_confirmation_safety`。最初的实现只有第一道，结果泄露了。详见[审查发现](#审查发现)。

**不编造。** 每张故事卡片都引用语句编号，提取完成后会逐一对照档案核实，编造的引用会被丢弃而不是保存。引语会和原始转写稿逐字比对。书稿里任何一段引语，只要追溯不到真实的语句，就会阻止导出。

**没有有效的同意，转写稿的文字不出本机。** 提取要求同时具备 `recording`、`ai_processing` **和 `third_party_services`** 三项同意。最后一项之所以单列，是因为模型服务商是另一家公司，适用它自己的数据保留政策和司法管辖。导出还额外要求 `family_sharing` 和 `print`。

**家属核对单最多 25 条。** 这不是默认值，是上限。§7.4 说得很清楚：让家属逐条审核事实，正是这类项目停滞不前的地方；“就再加几条”的冲动，就是失败的样子。

## 目录结构

```
lifestory/
  models.py       人生档案的数据结构（§8）。访问权限、放行和同意都在这里
  archive.py      本地优先的存储，每次写入都留版本
  language.py     一切和文字形态有关的处理：长度、分句、问句、
                  中文简繁与标点、人名、日期、同音字
  i18n.py         家属读到的每一句话，按家属的语言
  transcribe.py   本机 Whisper 转写；录音从不离开本机（§11、§12.1）
  ingest.py       转写稿解析，包括其他工具生成的中文格式
  extract.py      转写稿 → 故事卡片，并核实引用
  compose.py      全书构想（§9 第 2 步）和章节起草（第 3 步）
  validators.py   确定性校验（§10.4），纯代码，从不调用模型
  confirm.py      最多 25 条的家属核对单（§7.4）
  render.py       Markdown、DOCX、溯源表、印刷规格
  measure.py      问题产出率（§17）和分阶段工时（§18）
  llm.py          唯一知道“供应商”存在的模块（§11）
  cli.py          工作台（27 条命令；status 永远告诉你下一步）

operating-kit/    第 0 阶段的英文文档：操作手册、同意书、访谈指南、质检清单、政策
operating-kit/zh/ 上述文档的中文版，供说普通话的家庭使用
question-bank/    51 个中英双语的种子问题，标注产出率（§17）
samples/          公有领域的普通话测试录音说明、准确率评测脚本和演示成书
tests/            安全、全流程、命令行，以及每轮审查的回归测试
```

三个智能体，而不是十一个（§10）：**采访者**（尚未实现，第 0 阶段由真人采访）、**档案员**（`extract.py`）、**写作者**（`compose.py`），再加上确定性的校验程序。校验程序是代码而不是模型，因为它们永远不能有“创造力”。

## 测试

```bash
python -m pytest tests/ -q
```

共四个文件：

- `test_safety.py`：引用核实、引语忠实度、访问边界、同意门槛、时间顺序、核对单上限
- `test_pipeline.py`：导入→提取→放行→起草→校验→导出的完整流程，模型调用用桩代替
- `test_cli.py`：真实的命令入口：每条命令的 `--help`，端到端跑通 `review` 和 `answers` 两个交互流程，以及 `confirm` 的措辞检查
- `test_regressions.py`：审查中发现的每个缺陷各对应一个测试类，单独存放，让“哪里出过错”的历史一目了然

测试**不覆盖**文字质量。那是 §18 的“辨认测试”：三位家属盲读，判断“这听起来像不像她”，需要真人来读。

## 审查发现

第一版实现在跑任何真实案例之前就接受了审查。发现并修复了十个缺陷，每个都在 [`tests/test_regressions.py`](tests/test_regressions.py) 里有回归测试。

**其中一个很严重。** 家属核对单是唯一一份在书之前就交给家属的材料，而它引用事实条目时没有检查访问权限。一张私密的故事卡片被正确地拦住了，但从同一句话里提取出的一条事实条目，却原文照录进了家属核对单。在复现它的测试案例里，这张核对单会告诉一个女儿：她的母亲曾经送养过一个孩子，而母亲特意说过，女儿从来不知道这件事。

原因在于范围：访问控制只为故事卡片设计，事实条目被当成了元数据，而不是衍生内容。现在，*任何*衍生记录的可见性都根据来源现算，`build` 背后还有两道独立的检查。

其余九个，按后果轻重排列：

| | 缺陷 | 后果 |
|---|---|---|
| 2 | 提取窗口互相重叠，产生重复的卡片、事实条目和引语 | 一个案例约 30% 的卡片是重复的，§18 的统计被虚增 |
| 3 | `card.claim_ids` 从来没有被填写 | 核对单排序和“被排除事实”的校验都成了死代码 |
| 4 | `merge` 和校验程序对“逐字”的判断不一致 | merge 只做原始子串匹配，几乎把每条真实引语都标成了问题 |
| 5 | `check_names` 跳过了完全相同的名字 | 最强的重复信号，恰恰是它唯一忽略的情况 |
| 6 | 只要一个窗口失败，提取就丢掉全部成果 | 最昂贵的操作没有任何断点保存 |
| 7 | 每次保存都完整复制一份档案 | 一个普通案例 40 条命令就要占 30 MB |
| 8 | 重复导入同一份转写稿，会悄悄把一切翻倍 | 提取费用也跟着翻倍 |
| 9 | 问题库的回写功能从来没有接到命令行上 | §17 所说的护城河只建了一半 |
| 10 | `output_config` 和 `output_format` 同时传入 | 有覆盖掉 SDK 所设 schema 的风险 |

有一个怀疑**没有**成立：`check_draft_quotes` 看起来像是平方复杂度，但实测 1,800 条语句、40 段引语只需 0.6 秒，因为对真实引语的子串检查会立刻命中返回。所以没有改动。

### 第二轮：用中文跑一遍

把一段真实的普通话录音喂进流程后才发现，它处处默认是英文，而且大多数时候不报错。下面每一项都有回归测试。

**流程本身**

| 缺陷 | 后果 |
|---|---|
| 靠大写字母判断断句 | 一段 12.6 分钟的章节被转成了**一行**转写稿 |
| 防“整段粘连”的检查按空格计词 | 把那一行当作“100 个词”放行了 |
| 人名核对清单只找大写开头的词 | 对每一份中文转写稿都是空的 |
| 保留了 Whisper 混用的简繁字形 | 简体文字里夹杂着 75 个繁体字 |
| 中文默认用 `base` 模型 | 书名“朝花夕拾”被转成了“招花西石” |
| 没有任何提示词说明该用什么语言写 | 中文家庭会拿到英文的卡片、核对单和书 |
| 家属看到的文字和 DOCX 字体只有英文 | Georgia 字体没有中文字形，Word 悄悄替换了字体 |

**悄悄失效的检查**

| 缺陷 | 后果 |
|---|---|
| 重名检查只保留 `a-z` | 中文名字被完全跳过，而中文识别恰恰最容易出同音错 |
| 故事卡片标题只保留 `a-z` | 中文案例按标题去重的功能失效 |
| 引语检查拿整行来比 | 一段 15 字、错一个字的引语只得 0.2 分，会阻止导出 |

**顺带发现的更大问题**

| 缺陷 | 后果 |
|---|---|
| 命令行在 cp1252 控制台上打印中文 | 遇到第一个中文字就崩溃 |
| 参数解析器引用了一个已删除的常量 | **所有命令都坏了**；因为没有测试构建解析器，100 个测试全部通过。现在由 `test_cli.py` 覆盖 |
| `restrict` 只改了卡片本身 | 讲述人要求保密后，之前已放行的原话衍生出的事实条目仍会发给家属 |
| 强制放行后原话仍标着私密 | 讲述人自己决定放行的内容，永远过不了导出 |
| 转写不能断点续传 | 两次重启各丢掉一次长时间转写；现在每个片段都存盘 |

### 第三轮：从两段录音到一本成书

在把两段录音一路做成可印刷的书的过程中发现（见[演示](#普通话演示从录音到成书)）：

| 缺陷 | 后果 |
|---|---|
| 与一张保密卡片出自同一段原话的另一张卡片，可以不经提示就放行 | 放行它就等于放行了那段私密原话。第一次演示直到整本书写完、跑 `check` 时才发现 |
| 事实条目把讲述人称作“故事主人”或“我” | 家属核对单读起来像内部笔记：“长妈妈是一向带领着故事主人的女工” |
| 讲述人自问自答的反问句被当成了采访者的话 | 一段独白里的句子被分给了一个并不存在的采访者 |
| 用 `--hint` 提示的名字，看起来和真正听到的名字一样 | 一个提示词被写进了根本没提到它的地方，却会被当成已核实 |
| 一次普通话访谈超出了模型单次回复的长度 | 提取直接中断；现在过长的窗口会一分为二重试 |
| 问题库回写时丢掉了 `zh` 字段 | 第一次 `bank` 更新就会抹掉所有中文问题 |
| `extract` 每次都把所有访谈重跑一遍 | 第 2 次访谈要为第 1 次再付一次钱，讲述人下次审阅时会看到一堆已经决定过的近似重复卡片；中断后整次访谈从头来 |
| 转写完成后，`status` 仍然提示“去转写” | 这条专门告诉你下一步的命令，反而指回了最重要的手工步骤——核对转写稿——之前 |
| 两章讲了同一段内容，所有检查照样通过 | 书里隔一页就重复一段 |
| 没有任何东西引导质检人员去看可能编造的句子 | 随机“抽查三段”很可能漏掉“病家典衣当物”这种录音里从未提过的细节 |
| 中文书末写成“录音2次”和“2026-09-29”，构想页用半角冒号 | 都是小事，但正是这些让一本书显得像机器做的 |

## 已知不足

**起草的文字里可能有编造的细节，而且没有办法证明。** 这是唯一真正要紧的不足。校验程序核实的是*出处*，即引用和引语；在英文和普通话的实际运行中，这两项都守住了。但它们核实不了*细节*。像“I've never had anything clearer from anybody”这样的句子，以讲述人的第一人称写出、她却从没说过，照样能通过所有检查。普通话演示里的“病家只得典衣当物”（病人家里当掉衣物凑钱请医生）也是一样，录音里根本没有这句话。它最早出现在请家属确认的全书构想里。

这是结构性的，不是哪个模型的问题：一个既不是引语、也不是事实条目的编造细节，根本没有可以对照的东西。更强的模型编得少一些，但这个缺口依然存在。

代码*能*做的，是给人指方向。`check` 会按章列出那些和录音内容最不相像的句子。在演示里，它列出的 11 句中有 6 句是编造的。它看不出两件真事之间被编造出来的联系。[`05-质检清单.md`](operating-kit/zh/05-质检清单.md) 的“编造”一节就从这份清单开始，然后再请质检人员自选三段抽查。这一步是承重的，不能省。

**转写没有真正的说话人分离。** 说话人标签是根据话轮的样子猜的，短问句被当作采访者说的，而不是根据声音判断。在两个人、录音清楚的情况下大体没错，剩下的操作员在本来就要做的核对中顺手改掉。如果录音里有家属插话，要做好手工重标的准备。引入 `pyannote.audio` 可以彻底解决，但代价是一个沉重的依赖和一个 HuggingFace 令牌；在真实案例证明有必要之前，不值得。

**人名核对清单并不完整。** 英文里它能找出大写开头的误听，找不出小写的（“the severed side”其实是“the Severn side”）。中文里它靠词性标注和人名的特征；在两章真实的普通话录音上，它找出了所有家常式的称呼（长妈妈、阿长、衍太太、陈莲河），准确率 67–77%，漏掉了洪秀全、刚毅这样的名人，而这些名字识别本来就不太会错。转写稿还是要通读。

**方言是最难的情况，也是最要紧的情况。** Whisper 对标准普通话的表现尚可；一位八十岁、说上海话、粤语或带闽南口音普通话的老人，转写稿需要大量修改。如果真实案例证明如此，升级路径是 SenseVoice 或 Paraformer（FunASR）。它们对中文和方言强得多，同样在本机运行，只需替换 `transcribe.py` 的内部实现，不必重新设计。

**准确率数字来自朗读。** 普通话测试录音是一位训练有素的朗读者在念一篇准备好的文章（[`samples/`](samples/README.zh-CN.md)）。和老人的即兴访谈会差一些。拿到第一批真实访谈后，用 `samples/evaluate_asr.py` 对照人工校正过的转写稿测一测。

**照片处理只有骨架。** `Artifact` 模型记录了原件、衍生件、处理过程和分辨率，印刷校验也会检查它们，但没有导入和修复流程。第 0 阶段的照片工作是手工的，这是对的：§19 把照片修复放在第 3 阶段。

**没有采访智能体。** 第 0 阶段的访谈由真人进行，这也完全绕开了 §11 所说的语音识别风险。

**同意书是模板，不是法律文件。** 在向付费客户出示之前，需要按你所在地区的法律审核。§22 把档案归属和长期保存承诺列为待定的法律问题。

## 最值得守护的东西

按 §17 的说法，这里持久的资产不是代码，而是问题库，以及不断写回问题库的经验：哪些问题能引出一个*场景*而不是一段概述，对 1943 年出生和 1958 年出生的人又有什么不同。这些知识会随着案例越积越多，竞争对手抄不走。

`lifestory ask` 和 `lifestory tag` 就是为此而设的，`lifestory status` 会故意催你给问题打标签，`lifestory yield` 则是收获的地方。

不要让一个案例在问题没打标签的情况下结案。
