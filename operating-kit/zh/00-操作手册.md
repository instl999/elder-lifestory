# 案例操作手册

如何从头到尾跑完一个第 0 阶段的案例。规范 v2 §19 第 0 阶段。英文版：[`../00-case-runbook.md`](../00-case-runbook.md)。

第 0 阶段是**手工**交付的。工作台是为了让操作员更快，而不是取代操作员。如果您发现自己希望某一步能自动化，
就把花在这一步上的时间记下来：§14 正是靠这份工时记录，来决定第 1 阶段做什么。

下面的命令都写成 `lifestory <命令>`；实际运行时，在项目文件夹里用 `python -m lifestory <命令>`。
任何时候运行 `lifestory status <case-id>`，最后一行都会告诉您下一步该做什么。

**家属说英文？** 建立案例时用 `--language en`，同意书和访谈指南改用上一级目录里的英文版。

---

## 开始之前

- [ ] 在您要用的电脑上，`lifestory doctor --online` 全部显示绿色。
- [ ] 完整读一遍规范 §12，不是扫一眼。§12.2 的私密边界和 §12.3 的判断能力问题，是可能让这门生意关门的两件事，
      而且在当下都不容易意识到。
- [ ] 确定谁是操作员。每个案例都由一个具体的人负责。
- [ ] 确认委托的缘由（§3.1）。因为家人身体变化而来的“转折型”案例，节奏和“礼物型”案例不一样：14 天，不是 30 天。

---

## 1. 建立案例

```bash
lifestory new <case-id> \
  --owner "王秀英" --preferred "王奶奶" --language zh \
  --birth-year 1941 --sponsor "陈建国" --operator "您的名字" \
  --trigger transition --inheritor "陈建国"
```

`--language` 是家属使用的语言（`zh` 简体、`zh-Hant` 繁体、`en` 英文），家属读到的一切都跟着它走。
`--preferred` 是家里人对老人的称呼，核对单和书的扉页都会用它。如果老人有任何认知障碍，加上 `--mode assisted`。
这不是给人贴标签，它改变的是访谈的方式（§12.3）。

**现在就指定档案继承人**，不要拖到以后。§12.4 之所以存在，是因为总会有人在项目进行中离世，
到那时再临场商量这件事，是不可原谅的。

## 2. 录音之前，先取得同意

和讲述人坐下来，用 [`01-知情同意书-讲述人.md`](01-知情同意书-讲述人.md)。读给老人听，
不要把纸递过去让老人不看就签。

```bash
lifestory consent grant <case-id> recording --by "王秀英" --role story_owner
lifestory consent grant <case-id> ai_processing --by "王秀英" --role story_owner
lifestory consent grant <case-id> third_party_services --by "王秀英" --role story_owner
```

`third_party_services` 之所以单列，是因为转写稿会离开这台电脑，发到另一家公司，按照他们的数据保留政策、
在他们的司法管辖下处理，不归我们管。征求这项同意时，要把这一点直白地说出来。没有这一项，提取会拒绝运行。

协助模式下，必须由一位具体的人记录判断能力的评估：

```bash
lifestory consent grant <case-id> recording --by "王秀英" \
  --role story_owner --capacity-assessed-by "某某医生 / 您的名字"
```

**在这次谈话中，用大白话把 §12.2 的边界说出来：**

> “您跟我说的话，除非您说想写进书里，否则只留在我这儿。您的家人听不到录音。
> 如果您告诉我一些不想让他们知道的事，那是您自己的事，我不会传出去。”

这句话就是这个产品本身。早一点说，说到做到，并且一直守住。

## 3. 访谈

用 [`03-访谈指南.md`](03-访谈指南.md) 或 [`04-访谈指南-协助模式.md`](04-访谈指南-协助模式.md)。

**每次 15–25 分钟，不是一小时。** 每周做完一次短访谈，胜过一次长访谈半途而废（§7.2）。

记下您问的每一个问题。这是 §17 所说的资产，也是这里唯一竞争对手抄不走的东西：

```bash
lifestory ask <case-id> "您小时候住的地方，现在闭上眼睛还能看见的，是什么？" --topic childhood
```

录音。什么格式都行（手机录的 `.m4a` 也可以）；原始文件另外找个安全的地方保存。

## 4. 转写：在本机完成

```bash
lifestory transcribe <case-id> recordings/第一次访谈.m4a --hint "陈建国,东昌坊口,绍兴"
```

Whisper 在这台电脑上运行。录音只被读取，不会被复制、修改或上传。一个人的声音比文字更私密；
留在本地，就不存在需要额外同意、或者日后需要撤回的东西。

**用 `--hint` 给出您已经知道的名字**：家里人的名字、老家、街道。它们会在每 30 秒音频里提示 Whisper 一次。
讲述人自己的名字和称呼会自动加入。

在一段很难的真实普通话录音上实测：提示有帮助，但解决不了问题。不加提示时，7 个名字对了 1 个；加了提示，对了 2 个。
而且有一次，一个提示词被写进了一段根本没提到它的地方。这很要紧，因为一个从没说过的提示名，
看起来和真正听对的名字一模一样。所以提示过的名字会在核对清单上单独标出。**请确认每一个都真的在那里说过。**
提示值得用，但它代替不了您的耳朵。

中文默认用 `small` 模型，英文默认用 `base`；`--model medium` 更慢，也更准。在普通笔记本上，
`small` 转写一段 25 分钟的访谈大约也要 25 分钟。启动之后去做别的事就好。转写中途被打断（重启、断电）也不要紧，
用同一条命令再运行一次，会从断点接着转。

### 然后核对。这一步不能省。

命令会列出它认为听到的每一个人名和日期，每一个都附有第一次出现的时间点，方便您直接跳过去听。
**逐个对照录音核对。** 以下来自一次真实的普通话测试（鲁迅《朝花夕拾》的朗读录音）：

| Whisper 听成 | 实际是 |
|---|---|
| 陈连河、陈联合 | 陈莲河 |
| 眼太太 | 衍太太 |
| 冯瓢复英扬 | 凭票付英洋 |
| 宣元齐伯 | 轩辕岐伯 |
| 卢根 | 芦根 |

中文识别出错几乎都是同音字，所以核对清单会把读音相同的名字归到一组。Whisper 自己并不知道什么时候听错了名字：
在英文测试里，把 Margaret 听成 Margarit 的那些句子，平均对数概率是 -0.26，和完全正确的句子一模一样。
没有哪个置信度数字能替您把关。

不核对就提取，一个叫“眼太太”的人就会作为事实进入档案。

同时修正说话人标签。标签是根据每一轮话的样子猜的（短问句被当作是您说的），而不是根据声音。
这里没有真正的说话人分离。

*（普通词语的错误不在人名清单上：“憎恶”被听成“赠物”、“和蔼”被听成“和矮”，清单都找不出来。
演示成书里，“和矮”就这样进了书。要跟着录音通读转写稿。）*

## 5. 导入与提取

```bash
lifestory ingest <case-id> cases/<case-id>/transcripts/第一次访谈.txt --held-on 2026-09-12 --duration 22
lifestory extract <case-id>
lifestory labour <case-id> story_cards 95
```

**记下工时。** 每一次都记。第 1 阶段的决定，只会和这份记录一样可靠。

`extract` 只处理还没提取过的访谈，所以第二次访谈之后，它只会发送第 2 次访谈的内容。如果中途停了（断网、重启），
再运行一次，它会从最后一个完成的窗口接着做。想特意重做某一次访谈：`lifestory extract <case-id> --session 1`。

然后看看提取出了什么：

```bash
lifestory cards <case-id>           # 全部卡片
lifestory cards <case-id> --weak    # 还算不上场景的素材
lifestory show <case-id> sc_xxxx    # 查看一张卡片及其出处
```

弱卡片不是失败，而是下一次访谈的问题。每张卡片上的追问建议（`followup_question`）就是为此准备的。

## 6. 给问题打标签，记下它们引出了什么

```bash
lifestory tag <case-id> q_xxxx scene --card sc_xxxx
lifestory tag <case-id> q_yyyy summary
```

问题没打完标签，案例就不能结案。`lifestory status` 会故意催您做这件事。

## 7. 放行材料：慎重地，一张一张来

讲述人放行之前，什么都到不了家属手里。**和讲述人一起**过卡片：

```bash
lifestory review <case-id>
```

它会一张张展示卡片：故事本身，以及老人自己的原话，然后问：**r** 放行给家属，**k** 保密，**s** 以后再定，**q** 停下。
每张卡片由谁决定都会记录下来，每做一个决定就保存一次，所以中途停下也不会丢任何东西。

标为私密的卡片（提取时识别出的私下倾诉，§12.2）只有输入 `YES` 才能放行，而且只能在讲述人明确同意的情况下。
把一张卡片设为保密，也会同时收回它所依据的原话，所以由这些原话衍生出的任何内容也到不了家属核对单上。

两张卡片常常出自同一段原话。当讲述人把其中一张设为保密，而另一张卡片依据的正是这些原话时，`review`
会点出那张卡片的名字，并问 **“Keep those private too?”**（这些也一起保密吗？）：**y** 现在就一起保密，
**n** 留给讲述人以后决定。不管选哪个，这样的卡片以后要放行，都必须同样输入 `YES`，因为放行它，
就等于把那段私密的原话也一起放了出去。询问时，`review` 会告诉您原因。

老人拿不准的时候，答案就是“不”。以后随时可以再放行；可一旦印成书，就收不回来了。

*（单张操作：`lifestory release <case-id> <card-id> --to family --note "..."` 和
`lifestory restrict <case-id> <card-id> --note "..."`。）*

## 8. 家属核对单

```bash
lifestory confirm <case-id>
```

**发出去之前，先自己读一遍。** 家属会一字不差地读到每一条。每一条都应该是一句关于具体的人的平实陈述，
并且点出讲述人的名字或称呼。如果有哪一条用了讲述人的第一人称（“我1931年出生”），`confirm` 会把它列出来：
女儿读到这样的句子，会以为是她自己写的。把这些条目改写之后，再运行一次 `confirm`：

```bash
lifestory reword <case-id> <claim-id> "王奶奶1931年出生。"
```

改写后，这条事实的出处和状态都不变，原来的措辞会保存在备注里。家属一旦答复过某一条，它就不能再改写了，
因为家属认可的是那一版措辞；如有修改，用 `answer --correct` 记录。

把生成的核对单发给负责核对的家属。**25 条，15 分钟。** 如果您想再多加几条，请重读 §7.4：多出来的那几条，
正是让项目停滞的原因。

家属的答复回来之后，一次录完：

```bash
lifestory answers <case-id>
```

每一条：**y** 正确，**e** 改正（输入正确的说法），**n** 不对、但没人确定正确的是什么，**s** 跳过。
有争议的条目留在清单上，下次访谈再问。不要自己在几种说法之间做选择。

## 9. 全书构想，然后起草

```bash
lifestory direct <case-id>
```

**在写任何一章之前，全书构想必须经家属认可**（§9 第 2 步）。把生成的构想页发给他们。现在改结构，代价要小得多。

发之前先自己读一遍。各章的概要是模型用自己的话写的，里面的每一个事实，都应该是您在访谈中亲耳听到过的。
在普通话演示里，一个从没说过的细节（病人家里“典衣当物”凑钱请医生）最先就出现在这里，后来又被写进了正文。
家属发现不了这种问题，因为他们不在访谈现场。把它从构想页里删掉，同时也从
`cases/<case-id>/drafts/direction.json` 里对应章节的 `covers` 中删掉，因为起草时依据的是这个文件。

```bash
lifestory draft <case-id>
lifestory labour <case-id> drafting 180
```

然后自己把每一章都读一遍，全部读完。模型不知道自己什么时候写了会伤人的东西。

## 10. 校验与导出

```bash
lifestory check <case-id> --export
lifestory export <case-id>
```

阻断性的问题就是阻断性的。`--force` 是留给真正需要判断的情况的，不是为了赶在下班前做完。

`check` 还会列出 **“Spot-check these first”**（优先抽查）：每一章里和录音内容最不相像的句子，编造的细节通常就藏在这里。
在质检清单的“编造”一节签字之前，把每一句都追溯到转写稿。如果有警告说两章讲了同一段内容，其中一章就需要删改。

## 11. 印刷，亲手交付

订一本精装书。英文案例可以用 Blurb、Lulu 或 Bookvault；中文案例可以找国内有资质的印刷厂或按需印刷服务。
印刷规格在导出文件夹里（中文书的印刷规格附有出版内容审核的提示，页数太少时还会提醒不适合做精装）。

**能亲手交付，就亲手交付。** §19：一个女儿把一本印着父亲照片的精装书递到父亲手里的那一刻，
正是我们要检验的东西。一个 PDF 检验不了它。看看那一刻发生了什么，记下您看到的。

## 12. 结案

```bash
lifestory labour <case-id>       # 完整的工时明细
lifestory status <case-id>       # 还有没打标签的问题吗？
lifestory portfolio              # 第 1 阶段该做什么
```

对照 §18 的标准记录：

- 客户是否按预设价格付款，没有打折？
- 各阶段的直接工时
- 交付时人名、日期、亲属关系的错误数（目标：零）
- 辨认测试：三位家属盲读，“这听起来像她”，1–7 分
- 把六个月后的满意度回访记进日程

## 最容易犯的两个错误

**往家属核对单里加更多条目。** 感觉很负责，实际上是让项目停滞的原因。自己解决，或者下次访谈再问。

**因为委托人付了钱、又客客气气地要求，就放松 §12.2 的边界。** 委托人的钱买不到讲述人的私人经历。
如果哪天这让您觉得尴尬，说明它正在正常运作。
